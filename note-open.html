What open means here

A word everyone uses, so say what it buys you.

18 November 2026Baseline

Every project page on this site ends the same way: open to contributors. That sentence is worthless on its own. “Open” can mean a public repository with no explanation, or a banner that says contributions welcome above a codebase nobody outside the team has read. So here is what it means when we write it.

The repository. The code is public and the history comes with it. You can read the commit that made a decision, not just the file it produced — which is usually the part a newcomer actually needs.

The write-up. Each project has a case study with the same five sections: the problem, the constraints, what we built, what was hard, and where it landed. The fourth one is the point. A page that only lists features tells you nothing about whether the project is interesting to work on.

The parts that did not go smoothly. Constraints get named — a settlement window, a test budget, a chain that behaves differently from its documentation. On Sherwood that includes eight documented adversarial refusals: the cases the contracts explicitly reject, written down as a list rather than discovered later. That is the honesty we owe anyone deciding whether to spend a weekend on our code instead of someone else’s.

What open does not mean is that anyone can merge anything. A real project has a real owner who will read your change, which is the whole reason contributing to it is worth more than another tutorial. It means the door is unlocked and the room is lit.

If you want in, one address reaches everyone. Tell us which project and what you would like to work on; the case study and the repository are there so you can arrive with something specific.
